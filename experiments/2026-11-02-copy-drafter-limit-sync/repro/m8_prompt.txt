## What this optimization does

The model contains 36 Gated DeltaNet (GDN) recurrent layers in addition to its
other attention layers. With five speculative draft tokens, the original native
kernel verifies up to six tokens per request. For every verified token, it
computes a full FP32 recurrent state and writes that large state to memory.
Rejection sampling later determines which verified tokens were accepted.

The candidate retains the verification arithmetic but replaces these repeated
large state writes with compact FP32 records. Each token and value head records:

1. The 128-element correction delta that the original verifier calculated.
2. The 128-element normalized key that the original verifier used.
3. The actual rounded decay multiplier used by the original recurrence.

After the existing sampler chooses the accepted token count, a grouped CUDA
kernel replays the recurrence in forward token order and writes the final
accepted state. It also writes an intermediate state if that step crosses a
prefix-cache block boundary. This commit happens before native aligned-state
postprocessing/migration. Convolution states, cache allocation/layout, sampling,
and the rest of the model remain under the original implementation.

For scale, one layer's full per-token recurrent state is
24 × 128 × 128 × 4 = 1572864 bytes; its replay record is
24 × 257 × 4 = 24672 bytes, about 63.8 times smaller. This is a storage-size
comparison for the replaced per-token writes, not a claim of 63.8 times less
total traffic or 63.8 times faster inference. Verification still does the
original arithmetic, commit reads and writes accepted states, and the rest of
the model still runs. The observed C8 end-to-end gain is the measured 6–10%
range described above.

For an individual state element, the important arithmetic is a rounded FP32
multiply followed by the original FP32 fused multiply-add:

```
h = fma_rn(key[k], delta[v], mul_rn(h, actual_decay))
```

The actual decay is stored directly. Recomputing it from a logarithm, combining
the recurrence algebraically, changing operation order, or reducing record
precision is not covered by the exactness contract. Compiler flush-to-zero
behavior must also match the native implementation. The source checker verifies
that the verifier changes are limited to replacing state writes with records.

Each commit thread owns disjoint state elements throughout its recurrence.
This preserves source/final/boundary aliasing when a destination is also the
source slot. Within one request it reads its source elements before overwriting
them, and other threads do not need those elements. Request metadata must retain
the original scheduler's ownership invariants; this is not an arbitrary public
tensor API with bounds checks on every device-side metadata value.

### Decode versus prefill

This is a **speculative decode** optimization. Pure supported speculative decode
batches use replay. Prefill, mixed prefill/decode paths, ordinary unsupported
decode, and unsupported configurations retain the original implementation.
Cold long prompts spend substantial time in prefill, so a decode gain does not
imply a comparable reduction in cold time to first token. Warm prefix-cache
tests help separate reuse/admission/prefill costs from sustained generation.

### Meaning of lossless

The change introduces no new quantization and no intended approximation. Native
verifier outputs and accepted/boundary recurrent states are compared **bit for
bit**, including forward trajectories and captured real model inputs. The
FP32 arithmetic contract, source comparison, and direct state comparisons are
the strongest evidence for the changed operation.

Do not promise identical full generated text for every run of the distributed
server: the unchanged baseline itself showed run-to-run differences at fixed
seed and temperature zero. Finite tests are evidence, not a proof for every
possible model input. Distinguish native-state exactness from whole-server
nondeterminism, quality scores, and throughput benchmarks.

### Registered operators and metadata lifetime

`mbx_gdn_replay::verify` declares mutation of its preallocated output and replay
record tensors. It does not declare or perform mutation of the input state.
`mbx_gdn_replay::commit` declares mutation of an explicit list of state tensors.
Every device allocation used by the commit is supplied as a tensor argument;
the small pointer table is assembled in C++ and passed by value as kernel
parameters. No cached GPU tensor of raw pointers is exposed to Torch.

This matters for Torch's schema checking, input cloning, fake execution,
functionalization, current-stream behavior, and CUDA graphs. A hidden cached
pointer tensor could refer to obsolete allocations when a subsystem clones
inputs. The runtime retains strong references only for the current real step,
clears dummy/profile/capture metadata, and releases the step after committing.
Retaining profiling metadata can accidentally retain a very large dummy KV
allocation, so the lifetime test is deliberate.

The production image has no runtime `ctypes` loader, JIT compilation, research
source bind mount, or `/research` dependency. Build artifacts are an installed
wheel plus the two guarded integration edits. The original files also remain
inside the derived image as `.before-mbx-replay` copies for audit/testing.

## Applying this to another system

First inspect that system's actual image digest, Torch/CUDA ABI, GPU capability,
model architecture, TP/PP topology, state and activation types, GDN backend,
speculation, block size, cache mode, sequence limits, local launch patches,
available memory, and active workload. Compare them to the contract above.
Do not reduce or overwrite the other system's settings to make the guards pass.

If the system is the same supported two-GB10 stack, use the same verified image
on both ranks, verify its ID, preserve local configuration, snapshot and retain
the original pair, drain requests, stage, run the differential tests and direct
behavioral checks, benchmark its real workload, and only then select the new
image for normal launches. The extra 325.3 MiB per rank must fit without reducing
the existing KV allocation, context, concurrency, cache retention, or reliability.

If architecture, precision, backend, source version, shapes or cache lifecycle
differ, this package is not a validated drop-in. A port needs a fresh arithmetic
and integration review. In particular, a Triton backend, SiLU gate, different
state dtype, log-decay replay format, different speculative width, LoRA,
recoverssm mode, different block/cache mode, single-device deployment, or
different TP/PP layout is outside the current runtime contract. Do not bypass
the guards and assume the numerical result remains lossless.

## Debugging guide

| Symptom | First checks and interpretation |
|---|---|
| Build rejects source hash | Confirm the exact pinned base digest and compare source changes; do not just update hashes |
| ABI/load error | Confirm Torch `2.13.0+cu130`, CUDA 13.0, arm64 build, matching derived image on both ranks and installed `_C.so` |
| No replay-enabled log | Check environment and every runtime compatibility guard; unsupported config should keep original behavior and log the reason generally |
| Enabled log but no selection log | Exercise a real pure speculative decode; prefill/mixed batches intentionally keep original dispatch |
| Health passes but performance unchanged | Confirm real selection, C8 payload identity, output token counts, cold/warm cache state, acceptance rates, prefill share and competing work |
| Memory pressure | Check extra replay allocation, KV bytes unchanged, dummy/profile metadata lifetime, live process ownership and unified-memory release after stops |
| Graph/capture issue | Use operator registration/fake/AOT and CUDA graph tests; examine metadata lifetime and current-stream use; do not disable graphs silently |
| Prefix mismatch | Check accepted counts, request mapping, computed-token positions, boundary calculation and commit-before-native-postprocess ordering |
| Output mismatch | Reproduce against pinned original native kernel with real captured tensors; compare raw FP32/BF16 bits, source hash, compile flags and operation ordering |
| Apparent full-text change | Repeat baseline under identical conditions, inspect sampling/acceptance, then use state/logprob evidence; baseline nondeterminism is not proof that a kernel mismatch is harmless |
| Restart/launch failure | Check both node image IDs and original full launch/network settings, then retained original rollback pair; never silently lower capacity to make startup succeed |

For prefix-cache diagnosis, include the real asynchronous output hook and
established sparse retention policy. An earlier research fixture omitted that
hook and initially suggested a cache bug; it was corrected and the bug claim
withdrawn. Do not resurrect that disproven finding from intermediate files.
Generated-prefix tests deliberately cross 1632/3264 boundaries and compare
cached continuations with cold recomputation.

Interpret the generated-prefix fixture carefully: in the earlier matched
baseline and candidate, the first follow-up missed and the second follow-up
hit 1632 or 3264 tokens. This matches the established sparse retention policy.
That second hit follows a recomputing prefill on the first follow-up; it is not
proof that the initial generation's speculative boundary state was directly
reused. The direct bitwise boundary-state checks, native cache trajectories
and real captured-state comparisons provide the separate kernel-state evidence.
