perf(worker): trim the host heap once when startup freezes the GC heap

Base: candidate-53's series before 0784 (1107's 0001..0761, candidate-50's
0762..0777, 0779 and 0780, then 0781..0783). It applies with or without 0781
(#960), and 0785 (#998) applies on top. Round 0 (PR head 737aec88) was based
on the 1107 vLLM patch head 320021e3c4dbb202d911ab70e2cd924c75420488.

Rationale:
On 128 GB unified-memory GB10 nodes, host memory and the CUDA caching allocator
draw from the same LPDDR5x pool, so host heap pages that a process freed during
startup and never returned lower MemAvailable for as long as the server runs.
PyTorch's CPU tensor allocator in libc10.so (c10::alloc_cpu / c10::free_cpu) is
statically linked mimalloc, while Python objects and C++ containers use glibc
ptmalloc; neither returns freed pages to the OS unless asked.

Add trim_host_heap() in vllm.utils.mem_utils: libc10's mimalloc mi_collect(true)
(resolved from .symtab relative to _ZN3c108free_cpuEPv) and glibc
malloc_trim(0). Call it once, in freeze_gc_heap() after its last collection and
before gc.freeze(). The worker, the engine core and the API server each reach
freeze_gc_heap() at the end of startup. The worker now logs its startup memory
breakdown after the freeze, so the breakdown shows the trimmed state.

Quality:
No numerical, scheduling or serving-path change. Nothing runs after readiness,
and no flush runs on the prefill or decode path. On one tp3-switched rank (rank
0's shard, sp8), the trim returns 66 MiB of the worker's host heap at the end of
startup (mi_collect 59 MiB, malloc_trim 7 MiB) in 5 ms. RssAnon at readiness is
2736/2756 MiB against 2820/2820 MiB without the patch, and time to ready is
88.4/89.3 s against 89.0/87.8 s. MemAvailable cannot resolve the difference on
one node: its boot-to-boot spread there is about 0.15 GiB.

Round 1:
Round 0 added about 77 s to every tp3-switched boot. Its startup floor was
0.03-0.12 GiB a rank higher, and its post-prefill flush blocked the host on the
decode path. The time was spent in gc.collect(), not in the trims. Round 0 added
gc.collect() and trim_host_heap() to release_device_memory_under_pressure().
process_weights_after_loading() calls that function after every quantized module.
On a TP3 rank, under UMA pressure, it releases 277 times across the target's
and the draft's post-processing. Each full collection of the loaded heap takes
about 0.25 s, so loading took 109 s instead of 40 s. The 302 trims took 0.08 s
in all. Round 1 keeps only the end-of-startup trim:
- removed the gc.collect() and trim in the UMA pressure release, the
  reclaim_uma_memory() at the end of DirectModelLoader.load_model(), and the gc
  and trim in bind_weight_arena(). These are 1107's per-module flush and the
  points around it.
- removed the trims in DeviceMemoryProfiler, memory_profiling(), profile_run(),
  profile_cudagraph_memory(), the profiling teardown, capture_model(),
  freeze_gc_for_cudagraph_capture(), Worker.init_device(), the B12X preparation
  steps, determine_available_memory(), initialize_from_config(), the two warm-up
  flushes, the model cleanup, TileLang release_host_memory() and the executor's
  _trim_host_heap(). They ran mid-startup, the floor is set at readiness, and
  the final trim returns the same pages: RssAnon at readiness is the same as
  round 0's (2746/2745 MiB). The recipe fixes --kv-cache-memory-bytes, so
  profiling does not size the KV cache.
- removed the post-prefill flush (_pending_post_prefill_cache_flush and
  reclaim_uma_memory() after the first FULL decode step following an eager step).
  It blocked the host for 32-35 ms per call (116-120 ms with a large unfrozen
  heap) on the first FULL decode step after an eager step, and the next prefill
  then took about 61-67 ms to remap the memory. With --prefill-yield short,
  decode steps run between a long prefill's chunks, so the flush ran after every
  chunk: round 0's attribution measured stall-3 prefill under decode 2.37% slower,
  beyond the interval.
- removed reclaim_uma_memory() and its test, the capture-freeze trim test and the
  post-prefill flush test, and imported pytest in test_mem_utils.py, which
  calls pytest.skip.
